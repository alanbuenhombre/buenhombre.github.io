{ 02 } · Playbook · Design systems

De Figma a Storybook en un design system.

Cómo conectar diseño y código, con reglas claras, para que un design system se mantenga vivo sin depender de procesos pesados.

Para
Equipos pequeños: 1 diseñador + 1 ingeniero, o incluso un equipo sin ingeniero dedicado.
Duración
Lectura de 6 minutos. Se aplica desde el primer token.
Basado en
El proceso de Florian Boelter. Adaptado por Alan Buenhombre.
Postura
Figma documenta la intención. El código es la fuente de verdad.
{ 01 } — Principio base

Una regla antes que cualquier componente.

Esta es la regla más importante del playbook. Cuando la fuente de verdad está en el código, el drift se detecta con CI y las discusiones pasan de “cuál versión es la correcta” a “qué cambio queremos hacer”.

Lo que este playbook no es: una guía de Storybook desde cero ni un tutorial de Figma. Es la forma de conectar ambos mundos y de ponerle reglas claras al proceso.

{ 02 } — Arquitectura

Cinco capas, cada una con un dueño claro.

  1. { 01 } Figma Variables BASE (color, spacing, radius, type) + SEMANTIC (surface, text, action).
  2. { 02 } Cursor + Figma MCP Lee las variables y el código, y propone cambios.
  3. { 03 } Tokens en códigoFuente de verdad Tailwind o equivalente. Aquí vive la versión canónica.
  4. { 04 } Storybook Stories por componente, con sincronización unidireccional.
  5. { 05 } Adopción El producto usa la librería.

Por qué esta arquitectura

01

Los tokens se definen una sola vez y se exportan a cada plataforma.

02

Las stories son una ventana al código, no una copia.

03

Cada capa tiene un dueño claro.

{ 03 } — Fases

Cuatro fases: de los acuerdos a un proceso repetible.

Fase 0

Acuerdos antes de tocar nada.

Antes de crear un solo componente, define con tu ingeniero aliado:

Tip

Si no tienes ingeniero dedicado, este paso puede hacerse con un asistente de IA como Claude. Lo importante es que las decisiones queden escritas.

Fase 1

Tokens primero.

Objetivo: tener una base estable antes de los componentes.

  1. En Figma, crea las variables en dos niveles:
    • BASE: valores crudos (blue-600: #185FA5, space-4: 16px).
    • SEMANTIC: significado de uso (action-primary → blue-600, text-secondary → gray-600).
  2. Exporta las variables a un archivo JSON (tokens.json).
  3. Con Cursor + Figma MCP, genera la configuración de Tailwind a partir de esas variables.
  4. Revisa el resultado en un commit pequeño y pide aprobación de tu ingeniero aliado.
Tiempo aproximado20 a 30 minutos con IA, frente a una jornada completa de trabajo manual.
Primera contribución segura
Figma Variables→Cursor→PR de tokens→revisión→merge

Aunque nadie lo vea todavía, la base queda viva.

Fase 2

El primer componente.

Objetivo: establecer el patrón que se repetirá.

  1. Elige un componente simple y muy usado (botón, input, badge).
  2. Diseña y documenta sus variantes en Figma usando los tokens semánticos.
  3. Crea una rama en Figma para el componente. Al menos un diseñador revisa antes de llevarlo al archivo principal.
  4. Con Cursor, genera el componente en código y su archivo *.stories.tsx.
  5. Revisa el componente en Storybook antes de abrir el pull request.
  6. Abre el PR; el ingeniero revisa y hace merge.
Regla clave

El diseñador ve el componente en Storybook antes del merge, no después. Así el problema de tiempos desaparece.

Fase 3

Hacerlo repetible con RULES.md.

Después del primer componente, escriban juntos un archivo RULES.md que se cargue como contexto cada vez que se trabaje con IA. Debe incluir:

  • Estructura de carpetas y de componentes.
  • Convenciones de nombres, variantes y props.
  • Cómo usar tokens (qué clases o variables son válidas).
  • Cómo se escriben las stories (formato, argumentos, estados).
Qué cambia

El segundo componente ya no requiere repetir el prompt completo. Si algo se desvía, se ajusta la regla, no el resultado.

{ 05 } — Gobernanza

Cinco reglas para que el sistema no se desvíe.

{ 01 }

Ramas en Figma para componentes.

Mínimo una aprobación de diseño antes de mergear al archivo principal.

{ 02 }

Criterio de handoff.

El componente sale a código solo cuando está completo: pulido, documentado y con variantes probadas.

{ 03 }

El código es canónico.

Si Figma y código divergen, gana el código y el CI lo marca.

{ 04 }

Tokens antes que componentes.

Primero, acuerdo en las fundaciones; después, componentes.

{ 05 }

Repetibilidad con RULES.md.

El proceso se documenta una vez y se reutiliza.

Nota honesta

Estas reglas añaden un poco de carga. Vale la pena si el sistema se va a usar en serio.

{ 07 } — Caso de referencia

Lo que se acumuló en el caso original.

En el caso de estudio original: unos 6 meses, con 1 diseñador + 1 ingeniero trabajando en paralelo con el producto normal.

Fuente

Estas cifras vienen del caso de estudio de Florian Boelter, no de un proyecto propio.

Fundaciones

Tokens base + semánticos en Figma y en código.

Librería

~12 componentes documentados y vivos en Storybook.

Adopción

El equipo de front-end empieza a trabajar desde la librería.

{ 08 } — Siguientes pasos

Cómo aplicar este playbook.

  1. Define los acuerdos de la Fase 0 con tu ingeniero aliado.
  2. Exporta tokens desde tu archivo de Figma.
  3. Elige un solo componente para el piloto.
  4. Documenta las reglas en RULES.md después del primer componente, no antes.
  5. Mide cuántos componentes se acumulan en el primer trimestre.
